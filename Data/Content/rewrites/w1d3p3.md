# Week 1 - Day 3 - Implementation - A first look inside `playwright.config.ts`

In [Day 2 - Fundamentals](/learn/w1/d2/p2), you saw three settings in your configuration file. This
lesson goes through all the others, so that you recognize each one when you open the file. Later
lessons explain the most important settings in depth.

## Two ideas the file depends on

Several settings mention **CI**, which stands for **continuous integration**: a server that runs
every test automatically, for example each time someone changes the code. GitHub Actions, which you
declined in [Day 2 - Fundamentals](/learn/w1/d2/p2), is one such service.

The expression `process.env.CI` checks whether the tests are running on a CI server. It is true on
most CI servers and false on your computer. A setting written as `process.env.CI ? 2 : 0` therefore
means "2 on a CI server, and 0 on your computer". The `?` and `:` choose between the two values.

## The settings, one by one

Open `playwright.config.ts` in VS Code. The lines that start with `//`, or sit between `/*` and
`*/`, are comments. The settings are:

| Setting | Value in your file | What it does |
|---|---|---|
| `testDir` | `'./tests'` | The folder where Playwright looks for test files |
| `fullyParallel` | `true` | Runs the tests inside one file at the same time, instead of one after another |
| `forbidOnly` | `!!process.env.CI` | On a CI server, stops the run if a test was marked to run on its own with `test.only` |
| `retries` | `process.env.CI ? 2 : 0` | How many times Playwright runs a failed test again before reporting it as failed |
| `workers` | `process.env.CI ? 1 : undefined` | How many workers run tests at the same time. `undefined` lets Playwright choose. |
| `reporter` | `'html'` | The kind of report that Playwright creates after each run |
| `use` | see the next section | Settings that every test uses |
| `projects` | three browsers | The browsers that every test runs in |

`retries` is 0 on your computer on purpose. When a test fails while you are writing it, you want to
see the failure at once, not have it hidden by a second attempt.

## The use block

The `use` block holds settings that every test receives. In a new project it contains two:

| Setting | Value in your file | What it does |
|---|---|---|
| `baseURL` | a commented-out line | The address that short page addresses start from. With `baseURL` set to the banking website, a test can open `'/'` instead of the full address. |
| `trace` | `'on-first-retry'` | When to record a **trace**: a step-by-step recording of a test, with a snapshot of the page at each step |

`'on-first-retry'` records a trace only when Playwright runs a failed test again. Because `retries`
is 0 on your computer, this means that a failed test on your computer leaves no trace behind.

Many teams change this, so that a failure always leaves evidence. The example below shows a `use`
block with the settings that keep a trace, a screenshot, and a video only when a test fails. It
writes the block as plain data and prints it:

```ts
const useBlock = {
  baseURL: 'https://test-automation-banking.vercel.app',
  trace: 'retain-on-failure',
  screenshot: 'only-on-failure',
  video: 'retain-on-failure',
};

console.log(JSON.stringify(useBlock, null, 2));
```

**Output**

```output
{
  "baseURL": "https://test-automation-banking.vercel.app",
  "trace": "retain-on-failure",
  "screenshot": "only-on-failure",
  "video": "retain-on-failure"
}
```

**Explanation:** The three recording settings follow one rule: record the run, and keep the
recording only if the test fails. Recording every run wastes disk space, and recording nothing
leaves a failure that you cannot investigate. `JSON.stringify(useBlock, null, 2)` prints the object
across several lines, indented by two spaces.

## projects

The `projects` setting lists the browsers:

```ts
projects: [
  { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
  { name: 'firefox', use: { ...devices['Desktop Firefox'] } },
  { name: 'webkit', use: { ...devices['Desktop Safari'] } },
],
```

Every test runs once in each project. This is why the two tests in `example.spec.ts` produced six
results in [Fundamentals](/learn/w1/d3/p2). The file also contains projects for mobile browsers,
Microsoft Edge, and Google Chrome, but their lines are comments, so Playwright ignores them.

## Best practices

- Before you trust a test count, check how many browsers `projects` lists.
- Keep `retries` at 0 on your computer, so that a failure shows itself at once.
- Keep a trace, a screenshot, and a video for failed tests, so that every failure leaves evidence.

## Common mistakes

| Mistake | What you see | Fix |
|---|---|---|
| Expected a trace for a test that failed on your computer | The report has no trace | With `trace: 'on-first-retry'` and `retries` at 0, no trace is kept. Set `trace` to `'retain-on-failure'`. |
| Expected a trace for a test that passed | The report has no trace | `'retain-on-failure'` keeps traces of failed tests only. For one run, add the option `--trace on`. |
| Looked for a `baseURL` value | The line starts with `//` | It is a comment, so `baseURL` is not set. Remove the `//` and set the address to use it. |
