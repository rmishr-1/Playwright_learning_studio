# Week 1 - Day 1 - Fundamentals - Why automation, why Playwright

Software testing means checking that an application works the way it should. This lesson explains
what testing is, how automated testing differs from testing by hand, and why this course uses a
tool called Playwright.

## What software testing is

An **application** is a program that people use, such as a banking website or a shopping app.
Before an application is released, someone must check that it works. That work is called
**software testing**.

A tester works from a **test case**: a list of steps, and the result those steps should produce,
which is called the **expected result**. The result you see when you follow the steps is the
**actual result**. When the two are different, the tester has found a **bug**,
which is also called a **defect**.

| Part of a test case | Example |
|---|---|
| Steps | Open the login page, enter a valid email and password, and select **Login**. |
| Expected result | The account dashboard opens. |
| Actual result | An error message appears. |
| Outcome | The actual result is different from the expected result, so this is a bug. |

## Manual testing and automated testing

In **manual testing**, a person follows the steps of a test case and decides whether the result
is correct.

In **automated testing**, a program follows the same steps. The steps and checks of a test case,
written so that a computer can follow them, are a **test script**, or a test for short. You write
the script once, and a computer can then run it as often as you need.

| | Manual testing | Automated testing |
|---|---|---|
| Who follows the steps | A person | A test script |
| Who decides whether the result is correct | The person, using their judgment | The script only compares the actual result with the expected result it was given. |
| Can it notice a problem that nobody planned to check? | Yes. A person can see that something looks wrong. | No. It checks only what it was told to check. |
| Best suited to | Exploring a new feature for the first time | Repeating the same checks many times, for example every night |
| Cost of each run | High, because it uses a person's time | Very low, once the script is written |

This leads to the most important idea in this lesson.

> **Important:** **Automation does not find bugs.** It reports whether each check **passed** or
> **failed**. When a check fails, a person investigates and decides whether the failure is a bug.

## What you need before you automate a test

You need two things before you can automate a test:

1. **A known expected result.** You must know what the correct result looks like. Otherwise, the
   script has nothing to compare the actual result with.
2. **A way to find the element.** An **element** is one item on a web page, such as a button, a
   text field, or a link. The script must be able to find the element reliably every time, so
   that it can click it, type into it, or read it.

If either one is missing, the test cannot be automated. This is why some testing, such as exploring
a new feature without a fixed goal, stays manual.

## What Playwright is

**Playwright** is a free, open-source tool, made by Microsoft, for the automated testing of web
applications. **Open-source** means that anyone can read and use its code.

Playwright controls a **web browser**, the program you use to visit websites, in the same way a
person does. It opens pages, clicks buttons, and types text. Because it uses the application the way
a user does, from the first step of a task to the last, Playwright is called an **end-to-end
testing** tool. An end-to-end test checks a complete task, such as signing in and viewing an
account balance.

Playwright works with the three main browser engines. A **browser engine** is the part of a browser
that displays web pages.

| Engine | Used by |
|---|---|
| Chromium | Google Chrome and Microsoft Edge |
| Firefox | Mozilla Firefox |
| WebKit | Apple Safari |

You write Playwright tests in a **programming language**: a language with fixed rules for writing
instructions that a computer can follow. This course uses **TypeScript**, and the TypeScript
lessons begin in [Day 5 - TypeScript](/learn/w1/d5/p1). Playwright also supports JavaScript,
Python, Java, and C#.

## Why teams choose Playwright

Before Playwright, many teams used **Selenium**, an older testing tool that is still widely used.
With Selenium, teams usually add several other tools to build a complete setup. Playwright includes
those tools itself:

| Feature | What it does |
|---|---|
| Automatic waiting | A web page can take a moment to load. Playwright waits for each element to be ready before it clicks or types, so you do not need to add waits yourself. |
| Assertions | An **assertion** is a check that compares the actual result with the expected result. Playwright includes its own assertions. |
| Test runner | A **test runner** is the program that starts your tests and reports which passed and which failed. Playwright includes one. |
| Screenshots and video | When a test fails, Playwright can save screenshots and a video, so that you can see what happened. |
| Codegen | **Codegen** records your clicks in a browser and writes the matching test code. You use it in [Day 4 - Fundamentals](/learn/w1/d4/p2). |

Selenium remains a good choice for many teams. Playwright is newer, and it was designed to include
the tools that teams had to add to Selenium separately.

## Other kinds of testing tools

Playwright tests applications through a web browser. Other kinds of testing need other tools. One
of them tests an **API**, the way one program asks another for data without a screen. For example,
when a banking app shows your balance, it asks the bank's server for the number through an API.

| Kind of testing | What it checks | Example tools |
|---|---|---|
| Web interface (UI) | The application in a browser, the way a user sees it | Playwright, Selenium, Cypress |
| API | The requests and responses that programs exchange, without a browser | Postman, REST Assured, Playwright |
| Performance | How the application behaves when many people use it at the same time | JMeter, k6, Gatling |
| Mobile apps | Apps that people install on a phone | Appium |

Playwright can make a desktop browser imitate a phone screen. This is called **mobile emulation**.
It is useful for testing websites on phone-sized screens, but it does not test apps that are
installed on a phone. For those, testers use a mobile testing tool such as Appium.

## Where the effort goes

Learning a testing tool is only part of the work. On a typical project, about half of the effort
goes into learning the application: what it does, how people use it, and what the correct result
is for each task. The other half goes into three skills together: the programming language,
finding elements reliably, and organizing the steps and checks of each test.

Knowing the application matters as much as knowing the tool.
