# Week 1 - Day 5 - Fundamentals - Your first real test, and why assertions matter

In [Day 1 - Fundamentals](/learn/w1/d1/p2), you read that automation reports only whether a test
passed or failed, against a check that a person wrote. In this lesson, you see what happens when a
test has no check: it passes even when the feature does not work. Then you add a check, and watch the
test fail as it should.

## What a test looks like

Every test file in your project follows the same shape:

```ts
import { test, expect } from '@playwright/test';

test('a name that describes what the test proves', async ({ page }) => {
  // The steps of the test, using page.
});
```

| Piece | What it does |
|---|---|
| `import { test, expect } from '@playwright/test'` | Takes `test` and `expect` out of the Playwright package |
| `test('a name ...', ...)` | Creates one test. The name appears in the terminal and in the report. |
| `async ({ page }) => { ... }` | The steps of the test, as an async arrow function that takes out the `page` fixture |
| `page` | A new browser tab, opened for each test |

[Day 5 - TypeScript](/learn/w1/d5/p1) explains each of these parts of the language.

## Example: Sign in with a wrong password

An **assertion** is a check that compares what happened with what should have happened. If
the two differ, the assertion fails, and so does the test.

The example below signs in with a wrong password, and contains no assertion. Select
**Load into editor**, then select **Run**:

```ts
const { browser, page } = await launch();
await page.goto(BASE_URL);

// The email is correct, but the password is wrong.
await page.getByPlaceholder('Enter Email').fill('leela@gmail.com');
await page.getByPlaceholder('Enter Password').fill('WrongPassword1');
await page.getByRole('button', { name: 'Login' }).click();

await show(page);
await browser.close();
```

**Output**

The run finishes without an error. The screenshot shows the login page again, with the message
**Please Enter Valid Credentials** above the form.

**Explanation:** The sign-in failed, and the website said so. The code still finished without an
error, because each step did what it was asked to do: it filled in two fields and selected a button.
Nothing in the code checked what happened next.

## Write the same test in your project

Now write the sign-in as two tests in your own project. The first test has no assertion, and the
second has one. In the `tests` folder, create a file named `login.spec.ts`, as in
[Day 4 - Implementation](/learn/w1/d4/p3), and paste this code into it:

```ts
import { test, expect } from '@playwright/test';

test('a wrong password, with no check', async ({ page }) => {
  await page.goto('https://test-automation-banking.vercel.app/');
  await page.getByPlaceholder('Enter Email').fill('leela@gmail.com');
  await page.getByPlaceholder('Enter Password').fill('WrongPassword1');
  await page.getByRole('button', { name: 'Login' }).click();
});

test('a wrong password, with a check', async ({ page }) => {
  await page.goto('https://test-automation-banking.vercel.app/');
  await page.getByPlaceholder('Enter Email').fill('leela@gmail.com');
  await page.getByPlaceholder('Enter Password').fill('WrongPassword1');
  await page.getByRole('button', { name: 'Login' }).click();
  await expect(page).toHaveURL(/dashboard/);
});
```

In the integrated terminal, run the new file in Chromium only:

```bash
npx playwright test tests/login.spec.ts --project=chromium
```

**Output**

```output
Running 2 tests using 2 workers

  1) [chromium] › tests/login.spec.ts:10:5 › a wrong password, with a check

    Error: expect(page).toHaveURL(expected) failed

    Expected pattern: /dashboard/
    Received string:  "https://test-automation-banking.vercel.app/"
    Timeout: 5000ms

  1 failed
    [chromium] › tests/login.spec.ts:10:5 › a wrong password, with a check
  1 passed (8.1s)
```

**Explanation:** Both tests typed the same wrong password, and the sign-in failed in both. The first
test passed anyway, because it checked nothing. The second test failed, because its assertion expected
an address containing `dashboard`, and received the address of the login page. The output shows both
the expected value and the received value, which tells you what went wrong. In your terminal, the
error also shows the line of the test that failed, with a `>` next to it. Because a test failed,
Playwright also opens the report in your browser. Press **Ctrl+C** in the terminal to close it. Your
time and your number of workers may be different.

## How the assertion works

The line that makes the difference is:

```ts
await expect(page).toHaveURL(/dashboard/);
```

`expect(page)` says what to check, and `toHaveURL` says what it should be. `/dashboard/` is a
**regular expression**, a pattern for text, which here means "an address that contains `dashboard`".

Playwright's assertions **retry automatically**. `toHaveURL` checks the address again and again, for
up to five seconds, until it matches. If it still does not match after five seconds, the assertion
fails. This means that the assertion also works when the dashboard takes a moment to open.

A good assertion checks the **result** of the steps, not only that the steps ran. For a correct
password, both of these assertions check a result:

```ts
await expect(page).toHaveURL(/dashboard/);
await expect(page.getByText('Leela')).toBeVisible();
```

The first checks that the dashboard opened, and the second checks that it shows the user's name. For
a wrong password, the result to check is the message:

```ts
await expect(page.getByText('Please Enter Valid Credentials')).toBeVisible();
```

## Best practices

- Give every test at least one assertion that fails when the feature does not work.
- Check the result of the steps, such as the page that opens or the text that appears.
- Watch every new test fail once. Change one value, such as the password, and confirm that the test
  fails. A test that you have never seen fail may not be checking anything.

## Common mistakes

| Mistake | What you see | Fix |
|---|---|---|
| Wrote a test with no assertion | The test always passes, whether or not the feature works | Add an assertion that checks the result. |
| Checked something that is always on the page | The test passes, even when the steps did not work | Check something that appears only after the steps work, such as the dashboard address. |
| Left out `await` before `expect` | The test can finish before the check is done | Put `await` before every `expect` that checks the page. |
| Used a locator that matches several elements | `strict mode violation: ... resolved to 2 elements` | A locator must match exactly one element. Use text that appears once on the page, or add `.first()` to the locator. |
