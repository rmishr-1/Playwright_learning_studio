# Week 2 - Day 2 - Fundamentals - XPath, CSS, and three more assertions

An assertion decides whether a test passes, and a locator decides which element the assertion
looks at. [Week 1 - Day 5 - Fundamentals](/learn/w1/d5/p2) wrote one assertion, `toHaveURL`. This
lesson adds three more, `toHaveValue`, `toContainText`, and `toHaveText`, and two ways of writing
a locator by hand for an element that has no role, label, or placeholder to find it by.

## Two ways to write a locator by hand

[Day 1 - Fundamentals](/learn/w2/d1/p2) used `page.locator()` for the fields on the registration
form that have no placeholder, such as the email field. `page.locator()` takes a piece of text that
describes an element by how the page is built. That text can be written in one of two languages.

A **CSS selector** is a short pattern that names an element by its tag, its id, or one of its
attributes. An **attribute** is a named setting written inside a tag, such as `type='email'` inside
`<input type='email'>`. An **id** is an attribute that gives one element a name of its own, which
no other element on the page should share.

**XPath** is a second language for the same job. It describes a path to an element through the
page, and it can name an attribute along the way.

| To find | CSS selector | XPath |
|---|---|---|
| The button whose id is `Button1` | `#Button1` | `//button[@id='Button1']` |
| The input whose `type` attribute is `email` | `input[type='email']` | `//input[@type='email']` |

The pieces of each pattern:

| Piece | Language | Meaning | Example |
|---|---|---|---|
| `#` | CSS | The id that follows | `#Button1` finds the element whose id is `Button1` |
| `tag[attr='value']` | CSS | An element with that tag, whose attribute has that value | `input[type='tel']` finds the phone field |
| `//` | XPath | Anywhere on the page | `//input` finds every input, wherever it is |
| `[ ]` | XPath | A condition that the element must meet | `//button[@id='submitbtn']` finds the button whose id is `submitbtn` |
| `@` | XPath | The attribute that follows | `@placeholder='First Name'` means the placeholder is `First Name` |

[Week 1 - Day 4 - Fundamentals](/learn/w1/d4/p2) said that XPath breaks when the layout changes.
That was true of the example it showed, `//div[3]/button[1]`, which means the first button inside
the third `div`. An XPath like that describes a position, so moving the button breaks it. An XPath
that names an attribute, such as `//button[@id='Button1']`, finds the button wherever it is. It
survives a redesign in the same way that a CSS selector does.

Both languages are still a second choice. When an element has a role and a name, or a placeholder,
`getByRole` and `getByPlaceholder` describe what the user sees, and they come first.

## Example 1: Find two elements with XPath

The example below finds the email field and the Refresh button with XPath, and prints how many
elements each locator found. Select **Load into editor**, then select **Run**:

```ts
const { browser, page } = await launch();
await page.goto('https://demo.automationtesting.in/Register.html');

// Find the email field by its type attribute, and the Refresh button by its id.
const emailField = page.locator("xpath=//input[@type='email']");
const refreshButton = page.locator("xpath=//button[@id='Button1']");

// count() returns how many elements a locator found.
console.log(await emailField.count());
console.log(await refreshButton.count());

await browser.close();
```

**Output**

```output
1
1
```

**Explanation:** The `xpath=` prefix tells Playwright to read the text as XPath. Each locator found
one element, which is what you want before you act on it. A count of `0` means that the pattern
matched nothing. A count of `2` or more means that the pattern is not precise enough for an action,
because Playwright refuses to fill or click when it cannot tell which element you meant. The page
was searched only when `count()` ran, not when the locator was written.

## Example 2: Find the same two elements with CSS

The example below finds the same two elements with CSS selectors, and also prints the text on the
button:

```ts
const { browser, page } = await launch();
await page.goto('https://demo.automationtesting.in/Register.html');

// The same two elements, written as CSS selectors.
const emailField = page.locator("input[type='email']");
const refreshButton = page.locator('#Button1');

console.log(await emailField.count());
console.log(await refreshButton.count());

// textContent() returns the text inside an element.
console.log(await refreshButton.textContent());

await browser.close();
```

**Output**

```output
1
1
Refresh
```

**Explanation:** A CSS selector needs no prefix, because `page.locator()` reads its text as CSS
unless told otherwise. The counts are the same as in Example 1, because both languages found the
same elements. The text inside the button is `Refresh`, which is the kind of value that a text
assertion checks. This course writes a CSS selector where one is enough, because it is shorter. It
uses XPath where CSS cannot describe the path, which is the case in
[Day 4 - Fundamentals](/learn/w2/d4/p2).

## Example 3: Read the values that an assertion checks

A text field holds a **value**, which is the text typed into it, and an element such as a heading
holds **text**, which is the text written between its tags. The example below types an email, reads
the value back, and reads the text of the two headings:

```ts
const { browser, page } = await launch();
await page.goto('https://demo.automationtesting.in/Register.html');

// Type an email, then read back what the field holds.
const email = page.locator("input[type='email']");
await email.fill('ada@example.com');

// inputValue() returns the value that a field currently holds.
console.log(await email.inputValue());

// JSON.stringify() prints text inside quotes, so a space at either end becomes visible.
console.log(JSON.stringify(await page.locator('h1').textContent()));
console.log(JSON.stringify(await page.locator('h2').textContent()));

await browser.close();
```

**Output**

```output
ada@example.com
"Automation Demo Site "
"Register"
```

**Explanation:** The field holds the email that `fill()` typed. The main heading's text ends in a
space, which you cannot see on the page and which a text assertion must cope with. The form heading
is the word `Register` and nothing else. These three are the kinds of value that the three new
assertions check.

## Three more assertions

A **matcher** is the part of an assertion after `expect(...)` that says what should be true, such
as `toHaveURL`. This lesson adds three:

| Matcher | What it checks | Passes when |
|---|---|---|
| `toHaveValue('ada@example.com')` | The value of a field | The field holds that value, and nothing more |
| `toContainText('Automation Demo')` | The text inside an element | The text contains that piece, anywhere in it |
| `toHaveText('Register')` | The text inside an element | The whole text is that, apart from spaces at the ends |

Like `toHaveURL`, each of them retries for up to five seconds before it fails. `expect` works only
inside the test runner, so the assertions go in a spec file in your own project. In the `tests`
folder, create a file named `register-assertions.spec.ts`, and paste this code into it:

```ts
import { test, expect } from '@playwright/test';

test('the registration page shows its headings and keeps a typed email', async ({ page }) => {
  await page.goto('https://demo.automationtesting.in/Register.html');
  await expect(page).toHaveURL(/Register\.html/);

  // Type an email, then check that the field holds it.
  const email = page.locator("input[type='email']");
  await email.fill('ada@example.com');
  await expect(email).toHaveValue('ada@example.com');

  // Check part of the main heading, and the whole of the form heading.
  await expect(page.locator('h1')).toContainText('Automation Demo');
  await expect(page.locator('h2')).toHaveText('Register');
});
```

In the integrated terminal, run:

```bash
npx playwright test tests/register-assertions.spec.ts --project=chromium
```

**Output**

```output
Running 1 test using 1 worker
  1 passed (3.3s)
```

**Explanation:** The first assertion is the one from Week 1. In its regular expression, the
backslash before the dot makes the dot mean a dot, because a dot on its own means any character.
The other three assertions each name a locator, then a matcher. `toContainText` passes on part of
the heading, so the space at the end never matters. `toHaveText` passes because the whole text of
the `h2` is `Register`. It would also pass on the `h1` with `'Automation Demo Site'`, because it
ignores spaces at the ends. Your time may be different.

## What a failing assertion looks like

Change `'Register'` to `'Sign up'` in the last assertion, and run the same command again:

```bash
npx playwright test tests/register-assertions.spec.ts --project=chromium
```

**Output**

```output
Running 1 test using 1 worker

  1) [chromium] › tests\register-assertions.spec.ts:3:5 › the registration page shows its headings and keeps a typed email

    Error: expect(locator).toHaveText(expected) failed

    Locator:  locator('h2')
    Expected: "Sign up"
    Received: "Register"
    Timeout:  5000ms

    Call log:
      - Expect "toHaveText" locator('h2') with timeout 5000ms
      - waiting for locator('h2')
        14 × locator resolved to <h2>Register</h2>
           - unexpected value "Register"


      12 |   // Check part of the main heading, and the whole of the form heading.
      13 |   await expect(page.locator('h1')).toContainText('Automation Demo');
    > 14 |   await expect(page.locator('h2')).toHaveText('Sign up');
         |                                    ^
      15 | });

  1 failed
    [chromium] › tests\register-assertions.spec.ts:3:5 › the registration page shows its headings and keeps a typed email
```

**Explanation:** The `Expected` line is what the test asked for, and the `Received` line is what
the page holds. The call log shows that the assertion looked at the heading 14 times over five
seconds before it gave up, which is the retrying at work. The `>` marks the line that failed. Read
the `Received` line first when a test fails. If the page is right and the test is wrong, as here,
change the test. In your terminal, the error also shows the full path of the spec file, and the
path of a folder named `test-results` that holds details of the failure. Change `'Sign up'` back to
`'Register'` before you go on.

## Best practices

- Use `getByRole`, `getByPlaceholder`, `getByLabel`, or `getByText` first, and a CSS selector or an
  XPath only when the element has none of those.
- Name an attribute in an XPath, never a position, so that the locator survives a redesign.
- Print `count()` in the editor before you use a hand-written locator in an action, and expect `1`.
- Use `toHaveValue` for a field, and `toContainText` or `toHaveText` for a heading, a message, or a
  button.
- Use `toContainText` when part of the text is enough, and `toHaveText` when the whole text matters.

## Common mistakes

| Mistake | What you see | Fix |
|---|---|---|
| Used a text matcher on a field | `expect(locator).toHaveText(expected) failed`, with `Received: ""` | A field's contents are its value, not its text. Use `toHaveValue`. |
| Acted on a locator that matches two elements, such as `page.locator("input[type='text']").fill('Ada')` | `strict mode violation: locator('input[type=\'text\']') resolved to 2 elements` | Make the pattern more precise, such as `input[placeholder='First Name']`, or use `getByPlaceholder`. |
| Wrote `@` in a CSS selector | `Unsupported token "@type" while parsing css selector` | `@` belongs to XPath. Write `input[type='email']`, or start the text with `xpath=//`. |
| Expected a value that the page does not have | `Expected: "Sign up"` above `Received: "Register"` | Read the `Received` line. It is what the page holds, and the test must expect what the page holds. |
