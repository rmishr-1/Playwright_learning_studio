# Week 1 - Day 4 - Fundamentals - Codegen and finding your way around locators

A test can act on an element only after it finds the element. This lesson explains how Playwright
finds elements on a page, which ways of finding them keep working when a page changes, and how a
tool called Codegen suggests them for you.

## How a web page is built

A web page is written in **HTML**, a language that describes each element on the page. Each element
is written as a **tag**, such as `<button>` for a button or `<input>` for a text field. The HTML of a
page is also called its **markup**.

A **locator** is a piece of code that describes how to find one element on a page. Playwright
offers several kinds of locator. Some describe what a user sees, and others describe how the page is
built:

| Kind of locator | Example | Keeps working when the page is redesigned? |
|---|---|---|
| **id** or **class** | `#ng-x7f2q3` | Often not. Many tools create new ids and classes each time the site is built. |
| **XPath**, a path through the markup | `//div[3]/button[1]` | No. It breaks as soon as the layout changes. |
| `getByRole` | `page.getByRole('button', { name: 'Login' })` | Yes. It depends on what the element is and what it says. |
| `getByPlaceholder` | `page.getByPlaceholder('Enter Email')` | Yes. It depends on text that the user sees. |

An element's **role** is the kind of element it is, such as a button, a link, or a heading. Its
**accessible name** is the text that describes it, usually its visible label. A **placeholder** is
the grey hint text inside an empty text field.

These locators work the way a **screen reader** does. A screen reader is a program that reads a page
aloud for people who cannot see it, and it finds elements by role and name, not by markup. Playwright
also offers `getByLabel`, which finds a field by its label, and `getByText`, which finds an element by
the text inside it.

## Codegen and the Inspector

**Codegen**, short for code generator, records what you do in a browser and writes the matching
Playwright code. To start it, open the integrated terminal in your project and run:

```bash
npx playwright codegen https://test-automation-banking.vercel.app/
```

**Explanation:** The command opens two windows. One is a browser showing the banking website, and
the other is the **Playwright Inspector**, which shows the code. Each time you click or type in the
browser, a new line of code appears in the Inspector. Sign in with the email `leela@gmail.com` and
the password `Leela@123`, and watch the code appear. Codegen saves nothing, so copy any code you want
to keep before you close both windows.

Codegen chooses `getByRole` and `getByPlaceholder` whenever it can, for the reasons in the table
above. Treat what it writes as a first draft. It records every click, including clicks you did not
mean to make, so keep the locators and remove the rest.

## Example: Sign in with the locators Codegen suggests

In this studio, the editor on the right provides three helpers for your code:

| Helper | What it does |
|---|---|
| `launch()` | Opens a browser, and gives you a `page` to control |
| `show(page)` | Displays a screenshot of the page beside the editor |
| `BASE_URL` and `USERS` | The address of the banking website, and a list of users who can sign in to it |

The example below signs in to the banking website with the same locators that Codegen writes. Select
**Load into editor**, then select **Run**:

```ts
const { browser, page } = await launch();
await page.goto(BASE_URL);

// Find the two text fields by their placeholder text, and the button by its role and name.
const email = page.getByPlaceholder('Enter Email');
const password = page.getByPlaceholder('Enter Password');
const loginButton = page.getByRole('button', { name: 'Login' });

// Sign in as the first user in USERS, and wait for the dashboard to open.
await email.fill(USERS[0].email);
await password.fill(USERS[0].password);
await loginButton.click();
await page.waitForURL('**/dashboard');

// Show a screenshot of the page, then close the browser.
await show(page);
await browser.close();
```

**Output**

A screenshot of the account dashboard appears beside the editor, signed in as Leela.

**Explanation:** `fill` types text into a field, and `click` selects the button. `waitForURL` waits
until the page address ends in `dashboard`, which proves that the sign-in worked. `await` tells the
code to finish each step before it starts the next one. [Day 5 - TypeScript](/learn/w1/d5/p1)
explains `await` and `const` in full.

## Why the name of a test file matters

Playwright runs only the files whose names match its pattern for test files. By default, that means
names that end in `.spec.ts` or `.test.ts`. A file named `login.ts` is never run, even if it contains
a correct test. Playwright shows no error and no warning for it. [Implementation](/learn/w1/d4/p3)
proves this in your own project.

## Best practices

- Choose `getByRole`, `getByLabel`, `getByPlaceholder`, or `getByText` before an id, a class, or an
  XPath.
- Use Codegen for a first draft, then keep the locators and remove the clicks you did not mean.
- Name every test file so that it ends in `.spec.ts`.

## Common mistakes

| Mistake | What you see | Fix |
|---|---|---|
| Named a test file without `.spec.ts` | Its tests never run, and no error appears | Rename the file so that it ends in `.spec.ts`. |
| Copied everything Codegen recorded | The test works, but contains clicks that do nothing useful | Keep the locators, and remove the extra steps. |
| Used `getByRole('link', ...)` for an item on the dashboard | The locator finds nothing | On this website, the items on the dashboard are text, not links. Use `getByText`. |
