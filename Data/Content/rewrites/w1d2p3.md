# Week 1 - Day 2 - Implementation - Organizing a real project's folders and config

A new project keeps every test in one `tests` folder. As a project grows, that stops working well.
This lesson shows how teams organize test files into folders, how the configuration file finds
them, and which files to keep out of version control.

## Why one folder stops working

A real project soon has different kinds of tests: for example, tests of the web interface and
tests of an API. Different kinds of tests often need different setup. When all of them sit in one
folder, it becomes hard to run only one kind, such as only the API tests.

A common solution is to give each kind of test its own folder:

```text
tests/
  ui/
    login.spec.ts
    dashboard.spec.ts
  api/
    accounts.spec.ts
```

Group tests by what they have in common, such as the setup they need. Do not group them by the
order in which you wrote them.

## How Playwright finds test files

Two settings in `playwright.config.ts` decide which files Playwright runs:

| Setting | What it decides | Example |
|---|---|---|
| `testDir` | The folder where Playwright starts looking | `'./tests'` |
| `testMatch` | Which file names count as tests, inside that folder | `'**/*.spec.ts'` |

`testMatch` uses a **pattern**: a short description that matches many file names at once. In the
pattern `**/*.spec.ts`, the `**` means "in any folder", and `*.spec.ts` means "any file name that
ends in `.spec.ts`". A new project does not set `testMatch`, so Playwright uses its default
pattern, which matches every file whose name ends in `.spec.ts` or `.test.ts`, and the JavaScript
versions of those names.

The example below writes three configurations as plain data, so that you can compare them. It runs
in the editor on the right: select **Load into editor**, then select **Run**, and its result
appears in the **Console** tab below the editor. Every word in this code is explained in
[Day 5 - TypeScript](/learn/w1/d5/p1) and [Day 5 - Fundamentals](/learn/w1/d5/p2). For now, copy
it as written. It prints each configuration:

```ts
const newProject = { testDir: './tests' };
const uiOnly = { testDir: './tests', testMatch: 'ui/**/*.spec.ts' };
const uiAndApi = { testDir: './tests', testMatch: ['ui/**/*.spec.ts', 'api/**/*.spec.ts'] };

console.log('new project:', JSON.stringify(newProject));
console.log('UI only:    ', JSON.stringify(uiOnly));
console.log('UI and API: ', JSON.stringify(uiAndApi));
```

**Output**

```output
new project: {"testDir":"./tests"}
UI only:     {"testDir":"./tests","testMatch":"ui/**/*.spec.ts"}
UI and API:  {"testDir":"./tests","testMatch":["ui/**/*.spec.ts","api/**/*.spec.ts"]}
```

**Explanation:** `testDir` alone only says where to start looking. `testMatch` narrows the search
to the files you want. `JSON.stringify` turns each configuration into a line of text, so that
`console.log` can print it.

## Keeping files out of version control

**Git** is a **version control** tool: it saves the history of the files in a project, so that you
can see what changed and share your work with a team. The **`.gitignore`** file lists the files and
folders that Git must not save.

`npm init playwright@latest` writes these entries into your project's `.gitignore`:

```text
node_modules/
/test-results/
/playwright-report/
/blob-report/
/playwright/.cache/
/playwright/.auth/
```

| Entry | What it contains | Why Git ignores it |
|---|---|---|
| `node_modules/` | The installed packages | npm can install them again from `package.json` at any time. |
| `test-results/` | Screenshots, videos, and traces from a run | Playwright writes them again on every run. |
| `playwright-report/` | The report of the last run | Playwright writes it again on every run. |
| `blob-report/` | Report pieces for combining runs from several computers | Playwright writes them again on every run. |
| `playwright/.cache/` | Temporary files that Playwright keeps between runs | Playwright recreates them when it needs them. |
| `playwright/.auth/` | Saved sign-in details, used by tests that start already signed in | They can contain passwords or other private data. |

> **Important:** **If a test run creates a file again each time, it does not belong in Git.**
> Private data, such as saved sign-in details, never belongs in Git either.

> **Note:** Your project is not in Git yet, and this course does not require it. The `.gitignore`
> file is already written, so it costs nothing now and is ready when a team adds Git.

## Best practices

- Give each kind of test its own folder, and group tests by the setup they share.
- Keep `testDir` and `testMatch` in the configuration file, so that every run finds the same tests.
- Add any file that a run creates again to `.gitignore`.

## Common mistakes

| Mistake | What you see | Fix |
|---|---|---|
| Saved `test-results/` or `playwright-report/` in Git | The project grows large, and every change includes report files | Add the folders to `.gitignore`, and ask a teammate who uses Git to remove the saved copies. |
| Put every kind of test in one folder | It is hard to run only one kind, because their files are mixed together | Give each kind its own folder, and use `testMatch` to select it. |
