# Week 2 - Day 2 - Implementation - The same assertions, in a helper every test can call

In [Fundamentals](/learn/w2/d2/p2), the assertions sat inside one test. In this lesson, you place
the checks that every registration test needs in one function, next to `fillRegistrationForm` from
[Day 1 - Implementation](/learn/w2/d1/p3). You do every step in VS Code and in its integrated
terminal, in your own project.

## The problem with the Fundamentals version

Imagine ten tests that each fill the registration form and then check that the form holds the
values. Each test repeats the same three `expect` lines. If the email field changes, you edit ten
tests. [Day 1 - Implementation](/learn/w2/d1/p3) solved the same problem for the actions, by
writing them once in `fillRegistrationForm`. The checks get the same treatment.

## Step 1: Add a checking function to the helper file

Open `tests/registration-helpers.ts` and add this below `fillRegistrationForm`:

```ts
// Check that the form holds the values fillRegistrationForm gave it.
export async function expectFormFilled(page: Page, email: string) {
  await expect(page.locator("input[type='email']")).toHaveValue(email);
  await expect(page.getByPlaceholder('First Name')).toHaveValue('Ada');
  await expect(page.locator('#country')).toHaveValue('India');
}
```

The new function uses `expect`, so the file must import it. Add `expect` to the `import` line at
the top of the file, so that it reads:

```ts
import { expect, type Page } from '@playwright/test';
```

**Explanation:** `export` in front of the function makes it available to other files, as it does
for `fillRegistrationForm`. The email is a parameter, because it is the one value that changes from
test to test. The first name and the country are fixed, because `fillRegistrationForm` always fills
the same ones. The name starts with `expect`, so a reader of a test can tell that the line checks
the page and changes nothing on it.

## Step 2: Call both functions from a test

In the `tests` folder, create a file named `register-helpers.spec.ts`, and paste this code into it:

```ts
import { test } from '@playwright/test';
import { fillRegistrationForm, expectFormFilled } from './registration-helpers';

test('the form keeps the details of the first learner', async ({ page }) => {
  await fillRegistrationForm(page, 'learner.one@example.com');
  await expectFormFilled(page, 'learner.one@example.com');
});

test('the form keeps the details of the second learner', async ({ page }) => {
  await fillRegistrationForm(page, 'learner.two@example.com');
  await expectFormFilled(page, 'learner.two@example.com');
});
```

In the integrated terminal, run:

```bash
npx playwright test tests/register-helpers.spec.ts --project=chromium
```

**Output**

```output
Running 2 tests using 2 workers
  2 passed (4.1s)
```

**Explanation:** Each test is two lines, and both read the same way: fill the form, then check it.
The first `import` line names only `test`, because the test itself makes no assertion. The helper
makes them. Your time and your number of workers may be different.

## When a helper may contain an assertion

[Week 1 - Day 5 - Implementation](/learn/w1/d5/p3) gave a rule: a page object performs actions and
contains no assertions, so that tests expecting different results can all use it. `expectFormFilled`
seems to break that rule. It does not, because it is a different kind of helper. Its whole job is
to assert, and its name says so.

The rule to keep is that one function never does both. `fillRegistrationForm` fills the form and
checks nothing. `expectFormFilled` checks the form and fills nothing. A test that needs a different
check calls `fillRegistrationForm` on its own, and writes its own assertion. A test that needs the
usual check calls both.

## Why it is shaped this way

| Choice | Reason |
|---|---|
| The checks are in `registration-helpers.ts`, not in the spec file | Every test that fills the form can call them, and a changed locator is edited once. |
| The name starts with `expect` | A reader of a test sees at once that the line checks the page and does not change it. |
| The email is a parameter, and the other values are fixed | The email is the only value that `fillRegistrationForm` varies, so it is the only one the checker needs to be told. |
| Filling and checking are two functions, not one | A test can fill the form and then check something else, or check nothing, without changing the helper. |

## What a reviewer looks for

- Repeated `expect` lines live in one function, not in every test.
- A function that asserts is named for it, with `expect` at the start of its name.
- No function both performs actions and asserts.
