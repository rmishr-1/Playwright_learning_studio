# Week 2 - Day 3 - Fundamentals - Unique test data and dynamic locators

**Test data** is the set of values that a test types into an application, such as a name, an email,
or a phone number. This lesson builds test data that differs on every run, and builds a locator from
a value chosen at run time.

## Why a test needs a new email on every run

Many applications refuse a second sign-up with an email they have already seen. A test that types
the same email every time passes on its first run, and fails on every later run, because the
application reports that the email is taken. The test is correct, the application is correct, and
the failure comes from the data. The registration form at
`https://demo.automationtesting.in/Register.html` accepts any email, so nothing fails here. The
lesson builds the habit on this form, where a mistake costs nothing.

## Example: Fill the form with a unique email

The email box on the form has no placeholder text, so the example finds it with
`page.locator("input[type='email']")`. That text is a CSS selector from
[Day 2 - Fundamentals](/learn/w2/d2/p2), and it means "an `input` whose `type` is `email`". Select
**Load into editor**, then select **Run**:

```ts
const { browser, page } = await launch();
await page.goto('https://demo.automationtesting.in/Register.html');

// Build an email that differs on every run, and print it.
const email = 'learner' + Date.now() + '@example.com';
console.log(email);

// Find the email box by its type, and fill it.
await page.locator("input[type='email']").fill(email);

await show(page);
await browser.close();
```

**Output**

The Console tab shows one line, such as `learner1790134635273@example.com`, and the screenshot shows
the registration form with the end of that email in the **Email address** box. The digits differ on
every run.

**Explanation:** `Date.now()` from [TypeScript](/learn/w2/d3/p1) gives each run its own number, so
the email is new every time. The email is stored in a `const` before it is used, because the code
needs the same text twice: once to print it, and once to fill it.

## An attribute and a property

An `<input>` tag keeps two separate things that are both called `value`. An **attribute** is a
setting written in the page's markup, such as `type="email"`, and it does not change when you type.
A **property** is what the element holds right now, and it changes with every keystroke.
[Week 1 - Day 4 - Fundamentals](/learn/w1/d4/p2) introduced markup, and
[Week 1 - Day 5 - TypeScript](/learn/w1/d5/p1) introduced a property as a named value inside an
object. An element on a page is an object too.

| Attribute | Property |
|---|---|
| Written in the page's HTML, such as `type="email"`. | Held by the element while the page is open. |
| Stays the same when you type into the field. | Changes with every keystroke. |
| Read with `getAttribute('value')`, or matched with `@value` in an XPath. | Read with `inputValue()`. |

Read both, after typing an email:

```ts
const { browser, page } = await launch();
await page.goto('https://demo.automationtesting.in/Register.html');

const email = 'learner' + Date.now() + '@example.com';
const emailBox = page.locator("input[type='email']");
await emailBox.fill(email);

// Read the value attribute, which comes from the markup.
console.log('attribute:', await emailBox.getAttribute('value'));

// Read the value property, which is what the box holds now.
console.log('property:', await emailBox.inputValue());

// Count the elements whose value attribute equals the typed email.
console.log('matches:', await page.locator(`//input[@value='${email}']`).count());

await browser.close();
```

**Output**

```output
attribute: null
property: learner1790134638392@example.com
matches: 0
```

**Explanation:** `getAttribute('value')` prints `null`, a value that means "nothing is there",
because the markup of this box has no `value` attribute, and typing did not add one. `inputValue()`
returns the property, which is the email that was typed. `count()` returns the number of elements
that a locator finds, and the XPath `//input[@value='...']` found none, because `@value` reads the
attribute. You cannot find a field by the value you typed into it. To read that value back, call
`inputValue()` on the locator you already have.

## A dynamic locator

A **dynamic locator** is a locator whose text is built at run time from a value, instead of being
written out in full. A template literal builds it, with the value inside `${}`. The gender radio
buttons on the form have `value="Male"` and `value="FeMale"` written in their markup, so `@value`
finds them.

The example chooses a gender with `if` and `else`. An **`if` statement** runs the block after it
only when its condition is true, and `else` runs the other block otherwise. Choose a gender at
random, and select its radio button:

```ts
// Return 'Male' or 'FeMale', chosen at random.
function pickGender() {
  if (Math.random() < 0.5) {
    return 'Male';
  } else {
    return 'FeMale';
  }
}

const { browser, page } = await launch();
await page.goto('https://demo.automationtesting.in/Register.html');

// Choose a gender, then build the locator's text from the choice.
const gender = pickGender();
console.log('chosen:', gender);
const radio = page.locator(`//input[@value='${gender}']`);

// Select the radio button, and confirm that it is selected.
await radio.check();
console.log('checked:', await radio.isChecked());

await show(page);
await browser.close();
```

**Output**

```output
chosen: FeMale
checked: true
```

The screenshot shows the form with the chosen gender selected. Your run may choose `Male`.

**Explanation:** `pickGender()` returns one of two words, and the template literal places that word
inside the XPath. `page.locator()` treats text that starts with `//` as an XPath. The locator finds
the radio button because its `value` is an attribute in the markup, unlike the email that was typed.
`check()` selects a radio button or a checkbox, and `isChecked()` reports whether it is selected.

## The same test in your project

Now write both ideas as one test, and run it twice to watch the data change. In the `tests` folder,
create a file named `unique-data.spec.ts`, and paste this code into it:

```ts
import { test, expect } from '@playwright/test';

// Return 'Male' or 'FeMale', chosen at random.
function pickGender() {
  if (Math.random() < 0.5) {
    return 'Male';
  } else {
    return 'FeMale';
  }
}

test('the form takes an email that differs on every run', async ({ page }) => {
  await page.goto('https://demo.automationtesting.in/Register.html');

  // Build the email once, and keep it, so the assertion can compare against it.
  const email = 'learner' + Date.now() + '@example.com';
  console.log('email:', email);
  const emailBox = page.locator("input[type='email']");
  await emailBox.fill(email);
  await expect(emailBox).toHaveValue(email);

  // Choose a gender, build the locator from the choice, and select it.
  const gender = pickGender();
  console.log('gender:', gender);
  const radio = page.locator(`//input[@value='${gender}']`);
  await radio.check();
  await expect(radio).toBeChecked();
});
```

In the integrated terminal, run the test in Chromium only:

```bash
npx playwright test tests/unique-data.spec.ts --project=chromium
```

**Output**

```output

email: learner1790134987570@example.com

```

Run the same command a second time.

**Output**

```output

```

**Explanation:** `console.log` inside a test prints to the terminal, under the name of the test, so
you can see the data that each run used. The two runs typed two different emails, and both passed,
because each assertion compared the box with the email of its own run. The gender was the same in
both runs by chance. `toHaveValue` checks the property of a field, and `toBeChecked` checks that a
radio button or a checkbox is selected. Your time may be different.

## Best practices

- Build the unique value once, store it in a `const`, and use that `const` to fill and to assert, so
  both steps use the same text.
- Print the value with `console.log`, so a failed run tells you which data it used.
- Match `@value` in an XPath only against a value written in the markup, such as a radio button's.
- Read what a field holds with `inputValue()`, or check it with `toHaveValue`, never with an XPath.

## Common mistakes

| Mistake | What you see | Fix |
|---|---|---|
| Built the email inside `fill()` and again inside `toHaveValue()` | The assertion fails, because each call built a different email | Build the email once, in a `const`, and use it in both places. |
| Looked for a typed value with `//input[@value='...']` | The locator finds nothing, and an action on it times out | Use the locator that filled the field, and read it with `inputValue()`. |
| Typed the same email on every run of a sign-up test | The first run passes, and later runs report that the email is taken | Build the email from `Date.now()` and `Math.random()`. |
| Wrote the template literal in single quotes | The text `${gender}` appears in the locator as it is, and nothing matches | Put the text in backticks, not in single quotes. |
